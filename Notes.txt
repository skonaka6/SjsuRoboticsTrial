Setting up project environment (Arduino IDE)

Setup:
1) Download App executable from https://www.arduino.cc/en/software/, give -x perms if needed
2) Connect board via usb c*, LED on board should turn on
3) In IDE, select Tools > Processor: "ATmega328P (Old Bootloader), Tools > Boards: "Arduino Nano", and Tools > Port: "/dev/ttyUSB0"**
4) Add libraries (for this project, Adafruit MPU6050)
5) Ready to code. Click Verify and then Upload. Example code available in File > Examples > ... Website documentation available at https://docs.arduino.cc/built-in-examples/
6) Set Serial Monitor baud rate to be equal to the 6050's baud rate or output will be gibberish


*Some sites and quick google search say to use Mini B usb, but it seems that is for older products and recent years have implemented USB C.
**(Linux) If port doesn't show up, even after reconnecting the board, it's probably needs permission and BRLTTY may be conflicting. See section on Removing BRLTTY Conflict. Also section on Giving Access to Serial Ports
Removing BRLTTY conflict
Linux comes with a background service BRLTTY for braille display that will hog the port an Arduino Nano uses. Uninstall or disable+mask the service.
https://support.arduino.cc/hc/en-us/articles/29350073597468-Resolve-BRLTTY-conflict-on-Linux
In terminal:
# See if service is running
$ ps -C brltty
# See if BRLTTY is kicking out the board
$ dmesg
ftdi_sio 3-4:1.0: FTDI USB Serial Device converter detected
usb 3-4: FTDI USB Serial Device converter now attached to ttyUSB0
usbfs: interface 0 claimed by ftdi_sio while 'brltty' sets config #1
ftdi_sio ttyUSB0: FTDI USB Serial Device converter now disconnected from ttyUSB0
# if uninstalling completely, use following and reconnect the board
sudo apt remove brltty
# if only disabling, run these 4 commands and reconnect
sudo systemctl stop brltty-udev.service
sudo systemctl mask brltty-udev.service
sudo systemctl stop brltty.service
sudo systemctl disable brltty.service

#### Gimbal variable tuning
decreased loop frequency because overwriting terminal hundreds of times per second faster than needed is my pet peeve.
Also adjusted the var servo_target from using a (180 degrees / 9.8 m/s^2) unit conversion to half that (90 degrees / 9.8 m/s^2). Now it uses the full range of motion (0-180) of the micro servo. Originally I put in 180 degrees thinking that's the max extent expected (to rotate), that should line up with the max expected acceleration measurement (at rest, gravity). Well that turned out to be wrong. It's a lot more obvious when introducing the offset to 'center' the servo at position 90 to start with, but with the old conversion factor, the servo would max out and reach its 0-degree or 180-degree position when the board is rotated only to 45 degree angles. This mean the servo was rotating twice the magnitude of the MPU.

The rotation precision is much better as compared to the initial sketch. I think it's due to swapping around the order of operations (to unit-convert followed by constrain), so that's one extra item off the TODO list.


#### Removing the MPU Library
Built-in example i2c_scanner is a convenient way to get the hex address of the MPU: 0x68. I found this example during physical debugging.
This web page has a very thorough tutorial for almost exactly this project
https://howtomechatronics.com/tutorials/arduino/arduino-and-mpu6050-accelerometer-and-gyroscope-tutorial/
Essentially, do the following:
1 - pull up a datasheet for your MPU, this has register locations. The datasheet document number is listed as RM-MPU-6000A-00 but it's the same information as for 6050. The two apparently have identical specs, the difference being 6000 uses a different communication protocol. Datasheet found here:
https://cdn.sparkfun.com/datasheets/Sensors/Accelerometers/RM-MPU-6000A.pdf
2 - in setup(), initialize the WIRE library and reset the sensor to the Power Management Registers (datasheet chapter 3, Address '6B', PWR_MGMT_1) (oh would you look at that there's a TEMP_DIS bit). Should look like Begin transmission -> write register address -> write new register value (0) -> close transmission
Their tutorial sets the whole register to 0, but the datasheet says you reset all registers by setting the first bit to 1... this is something to experiment with later.
3 - optionally configure the MPU, i.e. the G value
4 - in loop, read data from accelerometer/gyro with Wire.write(register_address) and Wire.request(MPU, num_registers, true)
Data for each access is stored as 16 bits, or two bytes across TWO 8-bit registers, beginning at address 0x3B (see page 7 of datasheet, ACCEL_XOUT_H)
Datasheet note: _H and _L suffix are High Bits and Low Bits
TEMP_OUT is sandwiched between Accelerometer and Gyroscope OUTs. That's why some code examples you look up will tell you to read 14 bytes (14 registers) starting from ACCEL_X at 0x3B.
However if you don't care about TEMP, you can set the reading 'pointer' of the Wire to a new location like a JMP with:
 Wire.beginTransmission(MPU);
 Wire.write(0x3B); // Start with register 0x3B (ACCEL_XOUT_H)
 Wire.endTransmission(false);
and then read as many n bytes (registers) you want starting from that point with
 Wire.requestFrom(MPU, 6, true); // Read 6 total registers
Note that Wire.read() resolves into a single byte read from Wire, which is why we read() twice
5 - Assemble read data (bit shift) and divide by the LSB Sensitivity according to the table in datasheet page 30, 32
At Full Scale Range +-2g, divide accelerometer readings by 16384 LSB/g
At Full Scale Range +-250 */s, divide gyro readings by 131.0 LSB/degree/s
I don't understand the math behind this yet, or what LSB Sensitivity actually represents (just leave it on default in setup for now()), but these table is enough to work with for now. Add as research question post-project
6 - implement error correction or accelerometer anti-drifting or both.
Drift will nudge the servo to its range limit in about 2 minutes, even just leaving the board untouched. 

Tutorial and sample code cover minimizing drift and calculating roll and pitch from accelerometer data with an atan() func. I will try opting out of these parts for now to keep code lean since we don't require a robust solution at the moment.


#### Solving the Gimbal with accel measurements
This commit follows the same design logic as the sketch version before transitioning away from the MPU library:
1 - Read accelerometer measurement (will only need and use one axis. Choosing x arbitrarily).
 This is the step that changed the most between the first iteration and this one.
2 - map and constrain the accel measurement to degree position, and add offset. In the MPU library version, it used a conversion factor of 90 degrees / 9.8 m/s^2. Different formula, same idea.

Almost every tutorial out there insists on scaling down the accel measurement based on the +-G setting, but when you map it like this, it's not much more effort to just work with the raw data as is. Also saves some precision.
The only reason this commit took so long despite the small code change is that for some reason, at +-2G, 1G of gravity (MPU is at rest) should read about 16384 to ACCEL_OUT. That's why tutorials divide by 16384, that's 1G of gravity. But for some reason my arduino was receiving a value around 4200, nearly a quarter of the normal reading, affecting all axes! It took me a while to even realize this bug was here, and it even tricked me into thinking it was a setting misconfiguration for +-8G. It eventually disappeared, some time around when I tightened all the connections on the breadboard. But I don't even understand how that would affect the 15-12th bits of the data.

This version has one notable flaw. Another item for the todo list: When the offset variable is set to one side, and the MPU is tilted towards the other direction, it cannot reach its full extent of motion in that direction. This is because once the MPU hits a vertical alignment, any further rotation would only decrease the magnitude read by the accelerometer - it cannot produce a number any greater to make up for the counter-rotation of the offset to reach the far end of rotation in that direction.

#### The data window
One objective is to take one statistic (going to work with accelx) and track the last 128 samples in a rolling window, printing out the mean and standard deviation. This is a rather easy idea to implement:
1 - establish an array to work as the window int dataWindow[128]
2 - Use a pointer/index to track next insertion location dataWindowIndex
3 - record items in the array as normal, but upon reaching the end of the array, set the pointer/index back to position 0 and OVERWRITE old data. This is how we achieve the rolling window effect. If we want to maintain order, we'd use the index every time we read from the array, but mean and std are agnostic to this so we don't need the index beyond this point
4 - calculate and print mean and std from the array. As straightforward as can be.
Notes:
- be careful that the 16b integers can hold SUMs in the calculations. Use Longs if needed
- function parameter written as for calculateMean(int (*arr)[DATA_WINDOW_SIZE]){}. The array size is in fact needed
- ...and then you need to pass the address of the array in the function call calculateMean(&dataWindow);
- Use (*arr)[] when the declaration of the array is in another scope. Remember that (*arr)[] is different from *arr[] (operator precedence)
- In C, the best len(array) we have is sizeof(arr)/sizeof(arr[0])
- sq() and sqrt() are built-in funcs
- The window initializes with a bunch of 0's. Unless you want to complicate the mean and std dev functions to detect init cells and ignore them, the reported stats will be obviuously below actual values. The workaround I'll be using for this is to just SPRINT through the window the first time to populate it quickly, and then slow down the delay's "tickrate" after the first lap.
